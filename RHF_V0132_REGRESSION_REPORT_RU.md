# RHF v0.13.2 — возврат целей спасательных рейдов

## Симптом
После 0.13.1 пользователь сообщает: рейды приходят, разрушают всё вокруг и уходят; пленников игнорируют. Свежего Player.log после 0.13.1 в обращении нет, поэтому нельзя подтвердить единственную причину.

## Найденные дефекты исходника
- Обычный естественный rescue мог получить комбинированную штурмовую группу по `Rand.Chance(.44f)`, затем `SplitRescueWing` выводил часть спасателей в ванильный разрушительный рейд.
- Дебаговые чистые коалиции ошибочно помечались как комбинированный штурм и получали отвлекающих штурмовиков.
- Управление спасением шло через цепочку Harmony-патчей V123/V124, а не через прямую передачу контрола MapComponent.
- Если рассчитанный путь отсутствовал, fallback искал другой объект вокруг тюрьмы, даже не входящий в маршрут.
- В журнале предыдущих версий есть `Stalled` без приказов; выдача приказа ошибочно обновляла `LastProgressTick`.
- Поисковые операции за пропавшим VIP оставались исключены из выделенного rescue Lord.

## Исправление
1. Прямой вызов RHFRescueCommandV124 после высадки и на каждом 90-тиковом цикле. Отдельное управление фазами поиска, спасения и отхода.
2. Запрет неявного разделения спасателей; отвлекающие группы создаются только как отдельные запланированные/оплаченные партии.
3. Единый структурный ориентир: если путь с известной стоимостью не найден, ломать случайные стены/двери запрещено.
4. Таймер прогресса обновляется только при реальном продвижении к цели или уроне выбранной преграде.
5. Боец, которого RHF не смог закрепить за mission Lord, удаляется из ванильного Lord и получает Wait вместо разрушительного задания; ошибка диагностируется.
6. Debug action 33 — фактический командир, задание, состав, фаза, цели и последнее продвижение.

## Что не подтверждено
Локальная C# компиляция и игровые тесты RimWorld 1.7/Combat Extended недоступны. Компиляцию подтвердит GitHub Actions; поведение — тест №01 на чистом сохранении. Не выдавать исправление как подтверждённую работу всех видов рейдов.
