# RHF v0.13.3 — причины регрессии и контроль следующей сборки

Основа: точные исходники GitHub коммита v0.13.2 `1d0dac411c77a8dd467fb4936f56003ef9ac1717` (сверены Git blob SHA). Присланный пользователем `RaidersHaveFamilies.rar` содержит только установленный мод с `Assemblies/RaidersHaveFamilies.dll` и метаданными 0.13.2, не исходники.

## Причины

1. **Два и больше уведомлений.** В `RHFOperations.Deploy()` после реального `IncidentDefOf.RaidEnemy.Worker.TryExecute` мод вызывал собственный `ShowMissionLetter`. При этом сама ванильная генерация рейда отправляет письмо. Для поиска/мести `RHFReprisals` также отправлял письмо при **постановке события в очередь**, за 1200 тиков до появления рейдеров. Коалиционные операции вызывают `RaidEnemy` несколько раз для разных групп.
2. **Вмешательство старого ИИ.** Исходники сохраняли патчи v0.12.3 на `Deploy`, `MapComponentTick`, `Infiltrate` с собственной логикой `TakeMissionOwnership`, удаляющей бойцов из их Lord, и дополнительные патчи v0.12.4 на старые методы. Начиная с v0.13.2 операции управляются напрямую через `RHFRescueCommandV124`, поэтому эти патчи были одновременно лишними и потенциально опасными.
3. **Неоперативное преследование пленника.** `RHFRescueHoldToilV124` выдавал ванильный `DutyDefOf.Defend` с фокусом на пленнике. `JobGiver_AIDefendPoint` затем самостоятельно вел бойцов туда, даже если маршрут/приказ RHF ещё не был готов.
4. **Неполный захват новоприбывших пешек.** Некоторые варианты прибытия модовых фракций могут миновать своевременное связывание через `Pawn.SpawnSetup`. Старый патч v0.12.3 пытался восстановить их, но затем вмешивался в Lord. Встроен отдельный захват только действительно новых пешек текущей волны.

## Изменения

- Одно письмо из **самой ванильной** механики рейда: при активном RHF-рейде переопределяются `IncidentWorker_RaidEnemy.GetLetterLabel/GetLetterText`. За одну операцию пропускается один вызов принятия письма, включая вложенные перегрузки `ReceiveLetter`; других игроков/обычные события не затрагиваем. Отдельное `ShowMissionLetter` больше не вызывается. Письмо при планировании мести/поиска убрано.
- У старых патчей 0.12.3/0.12.4 отключено переназначение отряда. `MapComponentTick` напрямую вызывает `RHFRescueCommandV124`, `OnDeploy` и нужную фазу.
- Новый `Defs/DutyDefs/RHF_MissionHold.xml`: одна локальная самооборона и ожидание близ текущей позиции. Нет ванильных ThinkNode колониального штурма/разрушений. При отсутствии Def — резервный `DutyDefOf.Defend`, но с текущей позицией, а не камерой.
- Снимок ID пешек до каждого инцидента, захват только новых, человекоподобных пешек конкретной фракции текущей спасательной волны. Старые чужие рейдеры на карте не присваиваются.

## Приёмка (после зелёной GitHub Actions сборки)

1. Новая/чистая точка сохранения **до рейда**, не продолжать запущенный ранее v0.13.2 рейд: Lord и задания могут быть сохранены в сейве.
2. Один `01 — Спасение: пролом и побег`: **одно** RHF-письмо и задача спасения, без сноса посторонних помещений.
3. Один `06 — Спасение: коалиция`: единственное RHF-письмо, союзники не атакуют друг друга, группы выполняют назначенные задачи.
4. Отдельный поиск/месть по делу пропавшего VIP: **нет раннего письма** о рейде, уведомление приходит при реальном прибытии.
5. При отказе маршрута через `33 — Кто командует рейдом и зачем` проверить, что участники спасения имеют `RHFRescueLordJobV124`, а не `LordJob_AssaultColony`.

Проверки в CI — исключительно статические контракты. Это **не доказательство** компиляции или поведения RimWorld 1.7 + Combat Extended. После отправки ZIP GitHub Actions должен собрать DLL; текущую реплику игровым PASS считать нельзя.
