# NJR R020 — регресс разрушения стен спасательным рейдом №1
Дата: 23.11.2026. База: R019, код которой успешно компилировался в GitHub Actions, но игровое поведение №1 регрессировало.

## Сигнал с реальной карты
После R019 пользователь показал скриншот: несколько спасателей вокруг здания наносят удары по разным участкам стен и заходят несогласованно. По одному снимку нельзя установить, обязана ли конкретная стена разрушаться: для этого нужны данные о комнатах, дверях, турелях и достижимости. Но хаотичное переназначение направления атаки в исходниках подтверждается.

## Проверенные дефекты кода
1. `RHFRescuePlannerS41.Infiltrate`: каждые 180 тиков командир **выбирался заново** из живых солдат по текущей дистанции до пленника. Когда кто-то приближался, менялись лидер, стартовая клетка A* и назначенная преграда. Командир должен удерживаться до смерти, потери способности действовать, перевода на сопровождение или смены пленника.
2. `RHFObjectiveRouteV128.Resolve`: когда безопасный поиск **прерывался по пределу 12 000 расширений**, код трактовал `false` как «безопасного маршрута нет» и последовательно **разрешал стены**. Но превышение CPU-бюджета означает неизвестный результат, а не доказанную непроходимость.
3. `RHFRescueCommandV124.ClaimGroup`: смена ванильного Lord на спасательный не гарантировала отмену прежней `AttackMelee`/`AttackStatic` по постороннему строению. Рейдер мог продолжать бить старую цель, несмотря на новый боевой план.
4. При затяжном проломе планировщик считал отсутствие сближения с пленником застреванием и мог перестроить маршрут до уничтожения согласованной преграды.

## Исправления (3 C# файла)
- Устойчивый командир на каждого текущего пленника, замена только по необходимости.
- `BudgetExceeded`: после превышения лимита поиска не переходить к следующему более разрушительному режиму. Результат остаётся неполным; точка пролома **не назначается** только из-за прерванного A*.
- Закрепление действующей преграды в кэше маршрута до 2700 тиков (или до уничтожения/изменения обстоятельств); не менять стену из-за паузы, пока сапёр занят.
- При взятии рейдера под управление миссии прервать атаки по сторонним зданиям. Не отменять стрельбу по пешкам игрока, турелям и авторизованную работу сапёра/двери к стройплощадке капсулы.
- В режиме VerboseLogging писать смену реальной точки входа: прошлую и новую преграду, командира, длину маршрута и причину планировщика. Не писать этот лог каждый тик.

## Ограничения и статус
- Это **статическая правка исходников**. Отдельно прошли профильные тесты: `njr_225`, `csharp_lexical`, `rhf_124`, `rhf_128`, `rhf_132`, `rhf_151`, `njr_204`, `njr_223`, `njr_224` (все статические/модельные).
- Полный прогон старого набора тестов превысил локальное время: **нет результата PASS** для всей матрицы.
- C# DLL локально НЕ скомпилирована, игрового теста НЕ БЫЛО. На работоспособность R020 требуются успешный GitHub Actions и тест RimWorld.
- VIP #16, строительство пусковой, лаги всей игры и остальные 18 типов рейдов **в R020 не исправлялись и не подтверждены**.

## Приёмочные условия для №1
1. На той же карте рейд стартует полным отрядом, участники в одном миссионном Lord.
2. При нормальном проходе через дверь не выбран ни один лишний пролом. Если дверной путь реалистично перекрыт огнём турелей, разрешён согласованный безопасный пролом к цели.
3. После выбора преграды только назначенный сапёр бьёт её, остальные прикрывают и уничтожают непосредственные угрозы. Выбор другой стены требует уничтожения первой или значимого изменения обстановки.
4. Бойцы не продолжают старую ванильную атаку на постороннюю структуру после принятия миссии.
5. Если A* не уложился в лимит, никто не ломает стену только из-за этого. Бой и тактическое ожидание сохраняются.
6. После физического освобождения пленник уходит согласованно с охраной. Это существующее поведение R019, которое отдельно необходимо подтвердить.

Отчёт для следующей итерации: проверять логи `[NJR][R020]` и `[RHF][RouteV128]`, не объявлять №1 исправленным до реальной игры. Следующий приоритет после №1 — разбор строительства VIP №16 по runtime-журналу.
